    The SUDO_* Environment Variables¶

    Scope: Linux, bash, GNU coreutils, util-linux, sudo 1.9.x. Behaviour varies with sudoers policy and distro patches, so every claim below has a command you can run to verify it on your own machines. Check your version with sudo -V.

    1. Cheat sheet¶

    Two different families are often confused: variables sudo sets for the child process, and variables sudo reads from the caller.

    Variable Direction Meaning
    SUDO_USER set by sudo login name of the user who invoked sudo
    SUDO_UID set by sudo user ID of the user who invoked sudo
    SUDO_GID set by sudo group ID of the user who invoked sudo
    SUDO_COMMAND set by sudo the command plus arguments sudo was asked to run
    SUDO_PS1 read by sudo if set, PS1 in the child is set to this value
    SUDO_PROMPT read by sudo default password prompt, same role as sudo -p
    SUDO_ASKPASS read by sudo helper program used by sudo -A to obtain the password
    SUDO_EDITOR read by sudoedit editor for sudoedit, consulted before VISUAL and EDITOR

    Definitions: sudo(8), section ENVIRONMENT. sudoers can override the editor choice via the editor list and env_editor flag sudoers(5).

    Key mental model: SUDO_USER answers "who typed sudo", not "who am I now" and not "who should own the result". For "who am I now" use id(1).

    2. How they are created¶

    By default sudoers has env_reset enabled: sudo builds a fresh environment for the command instead of passing yours through, then adds the SUDO_* variables describing the caller sudoers(5). The work happens in the sudoers plugin, function rebuild_env() in plugins/sudoers/env.c.

    Consequences:

    • They exist only when sudo actually launched the process.
    • They describe the caller of that specific sudo invocation, so nesting changes them.
    • They are informational. They are not an authentication or authorization signal.

    3. Verify on your machine¶

    # authoritative definition for your installed version
MANWIDTH=80 man 8 sudo | col -b | grep -n -A 2 'SUDO_USER'

# what sudo preserves, removes and checks
sudo -V | sed -n '/[Ee]nvironment/,/^$/p'

# what the child actually receives
sudo env | grep '^SUDO_'

# caller vs current identity
sudo sh -c 'printf "now=%s caller=%s uid=%s gid=%s\n" \
            "$(id -un)" "$SUDO_USER" "$SUDO_UID" "$SUDO_GID"'

    4. Where they are genuinely useful (SUDO_* Environment Variables)¶

    4.1 Give created files back to the invoking user¶

    Classic case: a root installer that writes into the user's home. Use the numeric IDs, not the name: numbers need no NSS lookup and cannot be ambiguous.

    : "${SUDO_UID:?run this with sudo}"
: "${SUDO_GID:?run this with sudo}"

install -d -m 0755 -o "$SUDO_UID" -g "$SUDO_GID" "$HOME_DIR/.config/myapp"
install -m 0644 -o "$SUDO_UID" -g "$SUDO_GID" myapp.conf "$HOME_DIR/.config/myapp/"

# or after the fact
chown -- "$SUDO_UID:$SUDO_GID" /var/log/myapp/report.txt

    chown "$SUDO_USER": also works and picks the login group from the passwd database, but it fails in chroots or containers where the name does not resolve. See chown(1) and passwd(5).

    4.2 Find the real user's home and config paths¶

    Under sudo, $HOME is often /root, and $USER may be root, depending on always_set_home, set_home and -H. Resolve from the passwd database instead.

    uid=${SUDO_UID:-$(id -u)}
entry=$(getent passwd "$uid")
orig_name=${entry%%:*}
orig_home=$(printf '%s\n' "$entry" | cut -d: -f6)
orig_gid=$(printf '%s\n' "$entry" | cut -d: -f4)

    getent goes through NSS, so it also works with LDAP, SSSD and systemd-userdb, unlike grepping /etc/passwd getent(1), passwd(5).

    4.3 Drop privileges for the unprivileged parts of a root script¶

    Never compile, npm install, pip install or git clone as root when the result belongs to a user.

    # util-linux, root only, opens a PAM session, no password prompt
runuser -u "$orig_name" -- git -C "$orig_home/src/myapp" pull --ff-only

# util-linux, no PAM session, precise control
setpriv --reuid="$SUDO_UID" --regid="$SUDO_GID" --init-groups \
        --inh-caps=-all -- make -C "$orig_home/src/myapp"

# sudo again, applies sudoers policy to the target user
sudo -u "$orig_name" -- npm ci --prefix "$orig_home/src/myapp"

    Differences worth knowing: runuser is root-only and PAM-aware runuser(1), setpriv just sets credentials and keeps the environment setpriv(1), sudo -u re-enters policy evaluation sudo(8). su(1) itself recommends runuser for scripts run by root, and setpriv when no PAM session is needed. Always quote the name and use -- before the command.

    4.4 Per-user removable media paths¶

    udisks2 mounts under the desktop user, and the base directory differs by distro:

    • Debian, Ubuntu, Mint and Raspberry Pi OS use /media/USER/LABEL.
    • while Fedora, RHEL, Arch and openSUSE use /run/media/USER/LABEL.

    Older udisks1 used /media/LABEL.

    label=MYDisk
u=${SUDO_USER:-$(id -un)}
targetdrive=
for d in "/media/$u/$label" "/run/media/$u/$label" \
         "/media/$label" "/mnt/$label"; do
    if [ -d "$d" ] && mountpoint -q -- "$d"; then targetdrive=$d; break; fi
done

    More robust: do not depend on the user name at all. Resolve the label to a device and ask the mount table, then SUDO_USER becomes irrelevant findmnt(8).

    targetdrive=$(findmnt -rn -o TARGET -S "LABEL=$label" | head -n 1)

    4.5 Talk to the user's desktop session from a root script¶

    A root cron job or udev rule that wants to show a notification needs the user's runtime dir and bus, which are keyed by UID systemd.exec(5), pam_systemd(8).

    sudo -u "$orig_name" \
  XDG_RUNTIME_DIR="/run/user/$SUDO_UID" \
  DBUS_SESSION_BUS_ADDRESS="unix:path=/run/user/$SUDO_UID/bus" \
  notify-send "Backup finished" "MYDisk copied"

    Requires an active session for that user; pam_systemd creates /run/user/UID at login pam_systemd(8).

    4.6 Logging who asked for the operation¶

    logger -t mybackup "caller=${SUDO_USER:-$(id -un)} uid=${SUDO_UID:-$(id -u)} cmd=${SUDO_COMMAND:-$0}"

    Useful for correlating application logs with sudo logs logger(1). For real accountability use the sudo log itself and auditd, not this string, because the environment can be forged (section 5) sudo(8).

    4.7 Guard rails in scripts¶

    Refuse to run user-level tooling under sudo:

    if [ "$(id -u)" -eq 0 ] && [ -n "${SUDO_USER:-}" ] && [ "$SUDO_USER" != root ]; then
    echo "Do not run this with sudo. It writes to your home directory." >&2
    exit 1
fi

    Require sudo, and fail early with a clear message:

    if [ "$(id -u)" -ne 0 ]; then
    exec sudo -- "$0" "$@"
fi
: "${SUDO_UID:?could not determine the invoking user}"

    4.8 The read-side variables¶

    Keep a recognizable prompt in a root shell (SUDO_PS1 is read from your environment before the child env is rebuilt) sudo(8):

    export SUDO_PS1='[\u@\h \W]# '
sudo -s

    Custom password prompt, useful in deployment tooling:

    SUDO_PROMPT='[deploy] sudo password: ' sudo -v

    Non-tty password entry with sudo -A sudo(8):

    install -m 0700 /dev/null "$HOME/.local/bin/my-askpass"
cat > "$HOME/.local/bin/my-askpass" <<'EOF'
#!/bin/sh
zenity --password --title="sudo password"
EOF
SUDO_ASKPASS="$HOME/.local/bin/my-askpass" sudo -A -v

    The askpass helper must be owned by you and not writable by others. Never store the password in it.

    Edit root-owned files without running an editor as root:

    SUDO_EDITOR=nano sudoedit /etc/fstab

    sudoedit copies the file to a temporary file, runs the editor as you, then copies it back sudo(8), sudoedit(8).

    5. Where they bite, and the fixes¶

    Situation SUDO_USER Fix
    sudo ./script caller normal case
    sudo -u alice ./script run by bob bob intended: caller, not target
    root runs sudo -u alice ./script root use the target explicitly
    nested sudo inside a sudo script root capture identity once, at the top
    plain su inherited value survives su only sets HOME, SHELL, plus USER, LOGNAME for non-root targets su(1)
    su -, sudo su - unset login mode clears the environment su(1)
    doas ./script unset doas sets DOAS_USER doas(1), OpenDoas
    pkexec ./script unset no equivalent variable pkexec(1)
    cron, systemd unit, ssh root login unset fall back to id, or configure the user
    SUDO_USER=eve ./script eve forged, never trust it

    Reproduce the nesting and forgery cases:

    sudo sh -c 'echo "outer=$SUDO_USER"; sudo -u nobody sh -c "echo inner=\$SUDO_USER"'
SUDO_USER=eve SUDO_UID=1001 sh -c 'echo "trusted? $SUDO_USER"'

    5.1 A fallback chain that survives su, doas and cron¶

    /proc/self/loginuid holds the audit login UID, set at login by pam_loginuid. It is not changed by sudo or su, which makes it the best answer to "which human started this" on audited systems. The value 4294967295 means unset pam_loginuid(8), audit.rules(7), proc(5).

    orig_uid() {
    if [ -n "${SUDO_UID:-}" ] && [ "$SUDO_UID" != 0 ]; then
        printf '%s\n' "$SUDO_UID"; return 0
    fi
    if [ -r /proc/self/loginuid ]; then
        local l
        l=$(cat /proc/self/loginuid 2>/dev/null)
        case $l in ''|0|4294967295) ;; *) printf '%s\n' "$l"; return 0 ;; esac
    fi
    local n
    n=$(logname 2>/dev/null) || n=
    if [ -n "$n" ] && [ "$n" != root ]; then
        id -u -- "$n" 2>/dev/null && return 0
    fi
    id -u
}

    Caveats: loginuid needs audit support and pam_loginuid in the login stack, and it is often unset in containers. logname and who am i need a utmp entry, so they return nothing under cron or ssh -T logname(1), who(1).

    5.2 Do not trust the name, cross-check it¶

    if [ -n "${SUDO_USER:-}" ] && [ -n "${SUDO_UID:-}" ]; then
    if [ "$(id -u -- "$SUDO_USER" 2>/dev/null)" != "$SUDO_UID" ]; then
        echo "warning: SUDO_USER and SUDO_UID disagree, ignoring both" >&2
        unset SUDO_USER SUDO_UID SUDO_GID
    fi
fi

    This catches sloppy forgery, not a determined attacker. Authorization must come from sudo itself or polkit, never from an environment variable sudo(8), pkexec(1).

    5.3 Other traps¶

    • SUDO_COMMAND contains the full command line including arguments, so secrets passed in argv land in the child environment and are readable through /proc/PID/environ under the usual ptrace rules proc_pid_environ(5). Do not put secrets in argv, and do not try to re-exec by word-splitting SUDO_COMMAND.
    • HOME, USER, LOGNAME under sudo depend on sudoers and -H. Resolve from getent passwd "$SUDO_UID" instead of trusting them sudoers(5), getent(1).
    • Numeric IDs beat names for chown, install, setpriv, and for anything running inside a container or chroot.
    • Exotic sudoers configurations can change what survives. Test on the target hosts rather than assuming.

    6. Small reusable library¶

    # source this from a script that may or may not run under sudo
orig_uid() {
    if [ -n "${SUDO_UID:-}" ] && [ "$SUDO_UID" != 0 ]; then
        printf '%s\n' "$SUDO_UID"; return 0
    fi
    if [ -r /proc/self/loginuid ]; then
        local l
        l=$(cat /proc/self/loginuid 2>/dev/null)
        case $l in ''|0|4294967295) ;; *) printf '%s\n' "$l"; return 0 ;; esac
    fi
    local n
    n=$(logname 2>/dev/null) || n=
    if [ -n "$n" ] && [ "$n" != root ]; then id -u -- "$n" 2>/dev/null && return 0; fi
    id -u
}

ORIG_UID=$(orig_uid)
ORIG_ENTRY=$(getent passwd "$ORIG_UID") || ORIG_ENTRY=
ORIG_NAME=$(printf '%s\n' "$ORIG_ENTRY" | cut -d: -f1)
ORIG_GID=$(printf '%s\n' "$ORIG_ENTRY" | cut -d: -f4)
ORIG_HOME=$(printf '%s\n' "$ORIG_ENTRY" | cut -d: -f6)

as_orig_user() {
    if [ "$(id -u)" -eq 0 ] && [ -n "$ORIG_NAME" ]; then
        runuser -u "$ORIG_NAME" -- "$@"
    else
        "$@"
    fi
}

require_root() {
    [ "$(id -u)" -eq 0 ] || { echo "need root, try: sudo $0" >&2; exit 1; }
}

    Usage:

    require_root
as_orig_user mkdir -p "$ORIG_HOME/.cache/myapp"
chown -- "$ORIG_UID:$ORIG_GID" "$ORIG_HOME/.cache/myapp"

    8. Security summary¶

    1. SUDO_* is metadata for convenience and logging, never an access control input.
    2. Prefer id -u / id -un for current identity, getent passwd UID for facts about a user, and numeric IDs for ownership changes.
    3. Use sudoedit rather than sudo $EDITOR for root-owned config files.
    4. Keep secrets out of argv, because SUDO_COMMAND and /proc/PID/environ expose them.
    5. For audit trails, rely on sudo logs and auditd, not on env strings. Validate sudoers edits with visudo(8).

    9. One-line card¶

    who am I now      : id -un / id -u
who typed sudo    : SUDO_USER / SUDO_UID / SUDO_GID   (hint, forgeable)
who logged in     : /proc/self/loginuid, logname      (needs PAM/utmp)
facts about a UID : getent passwd UID
give files back   : chown -- "$SUDO_UID:$SUDO_GID" file
act as the user   : runuser -u NAME -- cmd
edit root files   : sudoedit, not sudo editor
